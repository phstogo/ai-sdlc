# 交付規則

## 測試與審查

1. G2 對每項關鍵驗收寫下「驗收 ID、公開入口、輸入及可觀測結果、覆蓋與缺口」。公開入口可以是 REST API、使用者操作、CLI 或模組正式介面。沿用專案既有決策和測試。若要改變既有介面、資料或部署約定，將決策、相容與移轉影響寫入規格；沿用專案 ADR 格式。新增測試入口有重大影響時按 G2 核准。沿用既有約定的小改可記錄假設，繼續已授權的可逆工作。
2. 為可安全實測的新關鍵行為或一般回歸先選一條使用路徑。由規格的範例或已知正確結果定義斷言，透過公開入口執行窄範圍測試。看到目標行為導致的失敗後，再實作讓該測試通過的最小改動；重跑該案例及受影響的既有測試。保存同一案例的前後命令、結果與版本。環境錯誤、缺依賴及編譯失敗不能作為行為測試的紅燈。已有充分測試或 baseline 無法安全實測時，記錄理由與目前可取得的證據。
3. 以公開介面的外部結果作功能斷言。依規格需要，可另用隔離資料庫或測試服務證據驗證持久化、副作用與恢復。不以私有方法或內部 mock 呼叫次數判定業務完成。為可靠性驗收保留必要的整合與持久化證據。
4. 用同一需求、規格及候選版分別寫下兩項審查結論，收在既有 `code-review` 證據。**規格符合度**按驗收 ID 核對入口、可觀測結果、缺漏及測試邊界。**程式品質**檢查專案規範、可維護性、相容性、錯誤與狀態處理。防禦性資安審查仍保留獨立的 `security-review` 證據。每項待修問題註明位置、影響與重驗證據。高風險仍取得獨立於實作者的驗證。

## 品質門檻

1. 在 G2 記錄品質基線的版本、必要檢查、命令或 CI job、適用範圍、及格條件與阻擋時點。重用專案既有規範、CI 設定或 `CONSTRAINTS.md`，並將重大變更連到核准的規格。沒有既定門檻時，用實測基線與需求提出數值和理由，依專案權責確認。輕量修改可記現有命令與合格條件。快速檢查儘早執行，耗時的整合與復原檢查安排於適用的合併或發行關卡。
2. 審查時比較基線與候選版的測試、斷言、工具規則、例外設定及 CI 執行範圍。查新增的 skip、only 或忽略註記，刪除或削弱關鍵斷言，降低門檻或掃描嚴重度，縮窄路徑、條件或測試資料覆蓋，允許檢查失敗後繼續，以及工具未執行或失敗卻顯示成功。將命令、案例執行數、跳過數和實際範圍與預期比對；人工判讀差異，保留等效替代驗證的證據。
3. 新增或修改會擋合併或發行的檢查時，在隔離環境執行實際命令，用合格對照證明應通過，用刻意不符合當前門檻的安全測試資料證明應阻擋。視檢查性質驗證工具錯誤或結果缺失時的行為，並核對上層 CI 有傳遞失敗。報告可產生、保護規則有配置與實際會擋下發行，各有自己的證據。
4. 在既有 `code-review` 證據記錄基線、比較範圍、發現和結論。若發現必要檢查被未經核准削弱或靜默繞過，留位置、影響、責任與候選版本，並在交付紀錄加 `blocking: true` 的開放發現。修正後用必做檢查重驗。若確有必要改門檻，回到 G2 記理由、影響與核准，再按新規格重驗。專案若允許中低風險例外，沿用原有具名與期限要求。

品質門檻與弱化審查參考 [Addy Osmani 的 constraint-driven-development](https://github.com/addyosmani/agent-skills/blob/main/skills/constraint-driven-development/SKILL.md)。發行觀測與回退參考 [shipping-and-launch](https://github.com/addyosmani/agent-skills/blob/main/skills/shipping-and-launch/SKILL.md)。

## 驗證選擇

每個驗收條件記錄 ID、可觀測的預期結果、對應的檢查與結果。優先用專案已有的命令與工具。先確認測試確實執行到對應案例和斷言，再採信退出碼；例如空測試集合、跳過、舊快取、覆寫環境或過寬的替身都要查清楚。

| 檢查 ID | 所需證據 |
| --- | --- |
| functional | 正常入口、關鍵驗收與相容／回歸證據。跨元件流程另列 integration。 |
| security-review | 對差異與信任邊界的人工或自審，涵蓋受影響控制及已知未驗證面。 |
| code-review | 規格符合度、實際入口、錯誤行為及可維護性。記錄審查者及缺口。 |
| reliability | 標準及高風險必備。依影響面列重試、重複寫入、並行、依賴失敗、恢復或負載檢查。 |
| integration | 高風險必須在授權測試環境驗證跨界面、部署入口或真實相容的整合。凡規格依賴跨元件或外部 API，即使標準等級也要列為必要檢查。G2 核對規格的相依項與必要檢查清單，並將清單寫入規格。檢查器無法從文字規格推斷相依項。 |
| security-tooling | 高風險必備。依面向選擇 SAST、依賴／鎖檔、秘密、映像或 IaC 掃描。適用的工具未執行則阻塞。 |
| recovery | 高風險必備。在隔離環境驗證回退、復原或受控向前修復，記錄驗證的情境及限制。 |

需求與設計階段將權限控制、輸入輸出、敏感資料、秘密、依賴、部署設定與稽核納入影響分析。API 應驗證伺服器端的角色／資料範圍、失敗時的安全行為及記錄。Web 應按範圍對照 [OWASP ASVS](https://asvs.owasp.org/) 的版本與適用控制。流程可對照 [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) 的開發、保護及弱點回應實務。記錄工具及規則版本、檢查目標、範圍、結果、未涵蓋面及證據。以防禦性程式審查、核准的掃描及正常入口的控制行為測試為限。

每一發現列位置、嚴重度、影響、責任、狀態及證據。未修復的重大／高嚴重度資安問題、關鍵資料完整性及核心功能失敗列阻擋。未解的中／低風險在不影響必要驗收且專案允許時，才可有具名核准、有期限的例外。掃描無發現限於該次範圍。高風險交付保留獨立於實作者的人工或 CI 驗證證據，及權責人的 G3；自審記錄仍然有用，但不能替代獨立證據。

## 版本綁定的交付紀錄

發行候選版採 Git 提交識別碼，於乾淨的隔離工作樹或 CI 重跑，將產物、工具輸出及核准紀錄存於受控證據目錄。必要時以 CI 建置產物摘要、設定及環境版本補充 Git 所涵蓋的範圍。變更需求、規格、程式、建置依賴或影響結果的環境後，重做受影響的把關或驗證。下列格式與檢查器用於發行判定，平常開發可沿用專案格式。

- 由 [交付紀錄範本](delivery-template.json) 複製一份並替換佔位值。最外層有 `risk`（`light`、`standard`、`high`），`candidate`（完整 Git 提交識別碼），`requirements`（需求文件附件），`specification`（規格附件），`acceptance`、`checks`、`approvals` 與 `findings`。
- 附件格式為 `{"path":"logs/verify.txt","sha256":"檔案的 SHA-256"}`。路徑相對 JSON 所在目錄，證據應為實際產生的紀錄，避免放原始秘密或個資。核對證據內容與來源，摘要可查出檔案被替換，無法認證核准人或測試真實性。
- `acceptance` 每筆有 `id`、`expected` 及 `checks`（一個以上必要檢查的 ID）。工程師確認這些條件與 G1 核准的需求完整相符。
- `checks` 每筆有 `id`、`required`（布林值）、`status`（`pass`、`fail`、`blocked`、`not-run`、`na`）、`detail`。通過時另有 `candidate`、`execution`（實際命令或人工審查程序）、`environment`、`evidence`（附件）。標準及高風險的驗證項以表格為最低要求。高風險再提供必要且已通過的 `independent-verification` 證據，記錄 CI run 或具名審查者。
- `approvals` 為 G1、G2、G3 陣列。每筆有 `gate`、`reviewer`、`record`（附件）、`requirements_sha256`。G2/G3 加 `specification_sha256`，G3 再加 `candidate` 與 `results_sha256`。結果摘要以同一指令加 `--digest` 產生，在請 G3 核准前提供。G3 核准後的結果、證據雜湊或發現清單有改就重取 G3。
- `findings` 每筆有 `id`、`location`、`impact`、`owner`、`severity`（`critical`、`high`、`medium`、`low`）、`status`（`open`、`resolved`、`accepted`）、`blocking`（布林值）。已修正時加必要重驗的 `check` ID。例外需 `reviewer`、`expires`（YYYY-MM-DD，以台灣日期含當日）、`record`（附件）。空陣列只用於已執行適用審查且確認未發現時。

執行 `python3 <skill>/scripts/release_gate.py <交付紀錄.json> --repo <已驗證的工作樹>`。退出碼 0 表示紀錄結構、證據檔摘要及版本關聯符合規則，退出碼 1 表示阻塞，2 表示輸入或執行錯誤。審查者另需查閱測試輸出、核准來源及掃描的有效範圍，腳本不替代這些判斷。若平台無法提供 Git、文件、測試或核准，照實標示待驗並保留交付紀錄。腳本也不含部署功能。

## 審查與收尾

從使用者角度走一次正常入口，核對已核准需求與交付內容。用測試資料核對資料寫入及副作用。涉及部署時，依可用機制記錄試行範圍、健康指標與觀測時間、繼續或停止條件、回退前置與責任人。回退後重跑健康檢查，確認狀態和資料符合預期。交付摘要列完成範圍、已執行命令與證據、未驗證項目、候選版及發行狀態。以既有 CI 或發行流程執行已授權的後續動作。
