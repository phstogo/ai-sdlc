# 階段交接規則

在有權限且下位接手者可讀的位置留存交接。沿用現有工單、工作計畫或變更紀錄。標準與高風險工作在跨階段或換人時更新，離開本輪前留下當前續做點。輕量工作的續做紀錄可只留狀態、來源、阻塞及下一步。

| 交接 | 上一階段要交付 | 接手者開始前核對 |
| --- | --- | --- |
| 探索 → 設計 | 需求版本、範圍、驗收 ID、假設、G1 狀態及尚待決策 | 可觀測的驗收條件足以開始所需設計。受核准約束的決策要等 G1。 |
| 設計 → 開發 | 規格版本、驗收對應的測試入口、品質基線、任務與相依、G2 狀態 | 任務已解鎖、範圍已授權、需先核准的規格已確認。 |
| 開發 → 驗證 | 候選版本或可安全接續的工作樹狀態、改動範圍、已做的測試與可重跑命令 | 核對實際版本及驗收範圍。只有合格乾淨工作樹上的完整 Git 候選版本可供正式發行檢查。 |
| 驗證 → 審查 | 同候選版的結果、環境、證據位置、未跑與失敗項目 | 確認必要檢查的範圍與證據版本。可先審查通過範圍，保留未決狀態。 |
| 審查 → 發行與維運 | 未解與已關閉發現、發行紀錄、G3 狀態、部署與回退手冊、權責人及監控條件 | 上線前核對 G3、候選版、結果摘要及部署授權。維運接手能定位實際部署版與恢復程序。 |
| 維運 → 修正 | 事件或缺陷 ID、受影響版、影響範圍、可讀證據、原驗收與發行紀錄 | 建立或連回工單，判斷回到最早受影響的階段。修正後重跑受影響檢查並取得對應核准。同類錯誤反覆出現時，將事件與防錯對照證據連回工單。 |

## 任務相依與進度

- 每個任務記 ID、驗收 ID、必要前置任務、狀態及完成證據。多條可平行工作時，先檢查是否碰同一資源或帶來相互影響。
- 狀態可使用現行工單系統的待做、進行中、阻塞、完成。前置尚未完成或缺必要權限時保留阻塞與原因。完成須有對應觀測或已完成的產物，按任務的退出條件判定。
- 不依賴阻塞項、且已授權的可逆工作可先做。優先維護一份任務與驗收對照，其他紀錄使用連結。

## 交接紀錄

可放在既有工單、計畫或變更紀錄，並以可讀連結指向實際產物。沒有候選版或未執行的項目如實標示。

```text
工作與階段：工單 ID／目前階段／狀態
權威資料：需求版、規格版、計畫或驗收 ID 的連結
工作基準：Git 版本或工作樹位置、未提交變更所在、候選版（如有）
進度與證據：已完成任務與證據、未完成任務與相依
阻塞與權限：原因、核准狀態與核准來源、負責解除的人或角色
下一個動作：一個目前可執行的任務或解除阻塞的條件、命令或入口、預期結果
```

## 續做與退回

1. 從交接紀錄定位工作，再以專案與原始證據核對版本、任務狀態、待決事項和核准範圍。交接文字不能當作完成證據或新授權。版本漂移時先確認哪些結果仍有效。若資料遺失，從可讀原始來源重建能證實的進度，其他項目標示未確認。
2. 核對正在編輯的檔案和未提交變更，避免覆寫其他工作。測試記錄指回實際跑過的版本與環境，觀測不符時在授權範圍重跑。
3. 驗證或審查失敗時，將問題連到驗收或品質檢查，回開發修正。若牽涉規格、品質門檻或需求，回最早受影響的階段並重取相應核准。保留原本的失敗證據，附上重驗結果及新版本。審查或發行結論仍依 [交付規則](delivery.md) 處理。
4. 上線後的異常保留監控、事件與回退證據，連回發行版本及修正工單。依授權與事故流程處理。事件關閉記錄恢復觀測與未解風險。

規格、計畫及任務檔作為跨對話交接的作法參考 [Addy Osmani 的導入指南](https://github.com/addyosmani/agent-skills/blob/main/docs/adoption-guide.md)。
